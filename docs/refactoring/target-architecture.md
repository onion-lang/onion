# Target compiler architecture

The target is a compiler whose phase boundaries are explicit, whose policy is
testable without running the whole compiler, and whose refactors preserve
observable language behavior. It is not a rewrite and does not require a new
IR or public API.

## Dependency direction

```text
tools
  -> public compiler facade
  -> pipeline contracts and phase adapters
  -> phase-local services
  -> AST / Typed AST / diagnostics / source abstractions
  -> runtime-independent utilities

backend adapter
  -> backend interface
  -> ASM implementation and emitters
```

The pipeline may construct concrete default phases, but phase-local policy
must not reach back into tools. Backend implementation details must not leak
past `AsmBackend`. Compatibility facades may point inward; new code must not
point outward through those facades.

## Phase shape

Each phase should converge on this shape:

1. A small adapter implementing `CompilerPhase[In, Out]`.
2. Explicit immutable input and output contracts where practical.
3. Pure classifiers or transformations for deterministic policy.
4. A narrow stateful shell for I/O, caches, class loading, or diagnostics.
5. Characterization tests at the phase boundary and focused unit tests for
   pure services.

## Parsing target

```text
ParsingPhase
  -> Parsing (reader lifecycle and JavaCC recovery)
     -> ParseDiagnosticBuilder
        -> SyntaxHintClassifier (pure classification)
        -> localized Message rendering
```

The first slice extracts `SyntaxHintClassifier` as a package-local pure service.
It returns a message key and literal arguments rather than localized text.
`Parsing` remains responsible for localization and exact final message
assembly. Later slices may separate source context and expected-token rendering,
but only if measurements still justify them.

## Rewriting target

`Rewriting` becomes an ordered composition of named transformations. Each pass
declares:

- accepted AST shape;
- output invariant;
- diagnostics it may add;
- ordering dependencies;
- whether it is idempotent.

Initial pass candidates must be selected by call-graph and test evidence, not
by line count. Feature lowerings that co-change with typing stay together until
a semantic contract is proven.

## Typing target

The existing four-pass structure remains. Improvements focus on:

- replacing concrete `Typing` dependencies with narrow capability traits;
- making unit-local state explicit in pass constructors or contexts;
- isolating name resolution, overload selection, and diagnostic reporting;
- keeping speculative typing rollback local and testable;
- preventing new root-facade accessors from becoming a second service locator.

No pass is split merely to reduce file length. A split must lower fan-out,
reduce mutable-state reach, or provide an independently testable invariant.

## Backend target

`AsmBackend` remains the only pipeline-facing ASM boundary. Large emitters are
split by JVM responsibility—class layout, method bodies, control flow,
closures, bridges, signatures—while stack discipline and bytecode verification
stay covered by end-to-end execution and verifier tests.

## Safety rails

- Fresh English and Japanese `testFull` runs at phase boundaries.
- Focused test suites for each changed service.
- Differential fixtures for parse diagnostics and AST transformations.
- Mutation sensitivity: deliberately wrong classification priority or message
  key must fail focused tests.
- Deterministic maintainability audit with JSON and Markdown outputs.
- `git diff --check`, tracked-generated-file checks, and clean-tree checks.
- Compile warnings recorded and driven to zero before a strict warning gate.
- Performance measurements use the existing readiness harness or a documented
  reproducible command; no threshold is invented from one host run.

## Compatibility rules

- Parser acceptance, AST shape, diagnostic code, location, wording, and hint
  priority are observable behavior.
- Typed AST and generated bytecode are compared through existing dumps and
  execution tests, not object identity.
- Public facades and CLI flags remain stable unless a separate user-facing
  change explicitly authorizes a break.
- Every extraction is independently revertible. Mechanical moves and behavior
  changes do not share a commit.

## Completion criteria

The program is successful when active hotspots have narrow responsibilities,
dependency direction is enforced, docs describe the code that exists, CI runs
the documented full contract, and future contributors can add a parser hint,
rewrite, typing rule, or backend emitter by following a short tested recipe.
