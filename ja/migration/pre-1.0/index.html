    1.0 への移行¶

    Onion は、まだ影響が小さいうちに、1.0 の前に構文と API を整理しています。 互換性を壊す変更を、コードの直し方と一緒にここにまとめます。

    1.0 以降は互換性を約束します。1.x でコンパイルできるプログラムは、 その後の 1.x でもコンパイルでき、意味も変わりません。

    ret は yield になりました¶

    do ブロックの最後の値は yield で書きます。

    // 以前
val sum = do[Option] { a <- getA(); b <- getB(); ret a + b }

// 現在
val sum = do[Option] { a <- getA(); b <- getB(); yield a + b }
    • 変わったこと: yield は予約語になりました。ret は普通の識別子に戻りました。
    • 表示されるもの: 古いコードでは「ローカル変数 ret が見つかりません」と表示され、yield を使うようヒントが出ます。
    • yield という名前の Java メソッド: バッククォートで呼び出します（例: Thread::`yield`()）。
    • プロジェクト全体を書き換える: onion migrate src/ tests/（ファイルやディレクトリを任意に指定できます）。 書き換えるのは do ブロックの ret だけです。ret という名前の変数・文字列・コメントは変えません。

    2147483648 の直前には - が必要になりました¶

    リテラル 2147483648（と 9223372036854775808L）は、-2147483648 のように単項 - のオペランドそのものである場合だけ有効です。 それ以外の場所では、以前は黙って最小値に化けていました。

    // 以前: コンパイルでき、意外な値になっていた
val a = 1 - 2147483648          // -2147483647（ラップアラウンドによる）
val b = -2147483648 as Long     // 2147483648: `as` は `-` より強く結合する
val c = -2147483648 / 2         // 1073741824: `/` は `-` より強く結合する

// 現在
val a = 1 - 2147483648L         // または 1L - 2147483648L
val b = -2147483648L            // または (-2147483648) as Long
val c = (-2147483648) / 2       // -1073741824
    • 変わったこと: 最小値の絶対値は、トークンではなく、それを符号反転する場所で検査します。
    • 表示されるもの: リテラルの位置に「整数リテラルがIntの範囲(-2147483648..2147483647)を超えています -- Long型リテラルにするには末尾にLを付けてください。」と表示されます（L 付きなら Long の範囲のメッセージです）。
    • 引き続き使えるもの: -2147483648、x + -2147483648、3 * -2147483648、-9223372036854775808L、0x80000000 のような 16 進数・2 進数のビットパターン。

    10進数の B/S リテラルは符号付きの範囲に収める必要があります¶

    10進数の Byte リテラルは -128..127、10進数の Short リテラルは -32768..32767 の範囲になりました。 Java と同じです。以前は、範囲外の値が黙って桁あふれしていました。

    // 以前: コンパイルが通り、意外な値になる
val mask: Byte = 255B           // -1
val port: Short = 40000S        // -25536
val n = -128B as Int            // 128: `as` は `-` より強く結合する

// 現在
val mask: Byte = 0b11111111B    // -1。ビットパターンとして書く
val port: Int = 40000           // Short には 40000 は入らない
val n = (-128B) as Int          // -128
    • 変更点: 2147483648 と同じく、128B と 32768S は - のオペランドそのものである場合だけ有効です。
    • 表示されるエラー: リテラルの位置に「整数リテラルがByteの範囲(-128..127、またはビットパターンとして0b11111111まで)を超えています -- ...」が出ます（S サフィックスなら Short）。
    • 引き続き使えるもの: 0b11111111B のような2進数のビットパターンと、0xFFFFS のように S を付けた16進数。
    • 16進数と B: 16進数リテラルの B は数字であり、接尾辞ではありません。0xAB は Int の 171、0xFFB は Int の 4091 です。Byte にしたいときは 0b11111111B か -1B と書いてください。
    • そのようなリテラルが Byte に収まらなくなった箇所（val x: Byte = 0xFFB、Byte 引数への f(0xFFB)）では、エラーにその理由を示すヒントが付きます。
    • まだ収まる箇所では何も報告されず、値だけが変わります。bs[0] = 0x1B は 27 を格納し（以前は 1）、val y = 0x7FB は 2043 です（以前は Byte の 127）。末尾が B の16進数リテラル（0x...B）をコードから検索してください。

    config ファイルの引用符付き String は、引用符を外して読むようになりました¶

    shape name = config のレコードは、二重引用符で囲まれた String の値を、引用された文字列として読みます。 これで、前後の空白を持つ値も print と parse を往復できます。

    # 以前: 引用符も値の一部だった
name = "Alice"          # "Alice" と読む（7 文字）

# 現在
name = "Alice"          # Alice と読む（5 文字）
name = "  Alice  "      #   Alice   と読む（空白を保つ）
name =   Alice          # Alice と読む（引用符のない値はこれまでどおり trim）
name = "\"Alice\""      # "Alice" と読む（引用符を文字として残す書き方）
    • 変わったこと: 引用符の中では、\" が引用符、\\ がバックスラッシュです。 それ以外のバックスラッシュはそのまま残るので、"C:\temp" は C:\temp と読みます。
    • 表示されるもの: 引用符を文字として使っていたファイルもそのまま parse に成功します。 そのため、エラーもヒントも出ません。値の外側の引用符が消えるだけです。 設定ファイルの中から " で始まる値を探してください。 閉じる " のない値や、中に裸の " がある値（"a" and "b"）は、行番号付きの Defect になります。
    • 対象は String 成分だけです: Int や Boolean などのスカラーは、これまでどおりに読みます。

    型 T の場所には T しか入らなくなりました¶

    ジェネリッククラスの中で、型パラメータ T で型付けしたフィールド・ローカル変数・引数への代入と初期化、 : T と宣言したメソッドの戻り値には、型 T の値だけが入ります。Java と同じです。 以前は T の上限に合う値なら何でも入り、次に読んだところで ClassCastException が出ていました。

    class S[T, U] {
  var t: T
  var u: U
public:
  def this(x: T, y: U) { t = x; u = y }

  // 以前: コンパイルが通り、new S[String, Integer]("a", 1) で t を次に読むと例外になる
  def f(): void { t = u }

  // 現在: 値が本当に T なら、検査なしのキャストを自分で書く
  def g(): void { t = (u as T) }
}
    • 変わったこと: 無関係な型変数（U）、上限の型（Object、CharSequence）、 具体的な型（"x"）の値は、T の場所に入らなくなりました。
    • 表示されるエラー: 値の位置に「E0000 型 T が期待されている箇所に、型 U を使用しました。」が出ます。
    • 引き続き使えるもの: T の値、T を上限に持つ型変数（[T, U extends T] での t = u）、null、 raw な Java の受け手に対する Java メソッドの引数（(o as ArrayList).add(u)）。 そこから読み戻した値（t = (o as ArrayList).get(0)）は T ではないので、キャストが必要です。
    • 同じ名前 T の型パラメータが二つある場合: class K[T] の中のメソッドの [T] は、別の T です。 このときエラーにはその旨のヒントが付きます。クラスの T を使うなら、メソッドの [T] を外してください。
    • 呼び出し: 継承したメソッド（Mid[U] extends Box[U] の中の set(o)）と、 型変数で型付けした受け手（xs: List[T] に対する xs.add(o)、b: Box[T] に対する b.set(o)）では、引数も検査します。
    • T? の場所: T の場所に入るものに加えて、null と T? が入ります。 そのため o: T? への o = u、o = uo（uo: U?）、o = "x" も E0000 になります（#2332）。 T? 型のコンストラクタ引数（def this(x: T?) に対する new Box[T](u)）は、T 型の引数と同じく E0021 になります。
    • 添字代入とリテラル: List[T] や Map[K, T] への xs[0] = u、m["k"] = u は、xs.set(0, u) と同じく E0000 になります（#2332）。 List[T] や Map[K, T] として使うリテラル [u]、[t, u]、["k": u] も E0000 です。 エラーにはリテラルの型（List[U]、型が混ざる場合は List[Object?]）が出ます。 List[Object] が期待される場所では、[t, u] は今も使えます。値が本当に T なら [(u as T)] と書いてください。
    • 継承したメンバーは U になりました: class Mid[U] extends Box[U] の中で、継承した get(): T は U です（以前は Object）。 U は null になりうるので、get().toString() は E0057 になります。Box の中では以前からそうでした。 get()?.toString() や get() ?: 代わりの値 と書くか、class Mid[U extends Object] のように null でない上限を付けてください。 Java のスーパークラスでも同じです。class MyList[T] extends ArrayList[T] の中の get(0).toString() も E0057 になります。
    • this は Mid[U] です: class Mid[U] の中の this は U を保ちます。 val me = this、id(this)、[this]、() -> this を通しても同じです。 そのため same(this) は継承した same(o: Box[T]) に渡せ、me.get() は U です（以前は raw な Mid で、me.get() は Object でした）。
    • 型引数が異なる分岐: if b { [t] } else { [u] } は raw な List になります。 Object が期待される場所ではコンパイルできます。List[T] が期待される場所では、[u] の分岐が E0000 になります。
    • onion migrate の書き換え規則はありません（意図的です）: 機械的にできる書き換えは (u as T) の挿入だけです。 それでは、この検査が見つけるバグをそのまま隠してしまいます。エラーを一つずつ読んで判断してください。

    空の [] / [:] は、隣の要素の型になりました¶

    リストリテラル、またはマップリテラルの値に空の [] / [:] があると、他の要素が揃っている型として扱います。 以前は、リテラル全体が Object に広がっていました。

    val adj = [[1, 2], []]

// 以前: List[Object] なので、adj[1].add(5) は E0005 で、次の行はコンパイルできた
adj.add("header")

// 現在: List[List[Int]] なので、adj[1].add(5) はコンパイルでき、次の行は E0005
adj.add("header")

// 以前の型を保つには、型を注釈する
val xs: List[Object] = [[1, 2], []]
    • 変わったこと: 空のリテラルは、隣の要素の後に、その型で型付けされます。要素の評価順は、これまでどおりソースの順です。
    • 表示されるもの: 異なる種類の要素を混ぜたコードや、List[Object] の引数に渡したコードで、List[List[Int]].add(String)（または Map[String, List[Int]].set(...)）を示す E0005 が出ます。
    • そのまま動くもの: 明示した型注釈が優先されます。型の分かる隣の要素がないリテラル（[[], []]）は、これまでどおりです。

    多重定義された拡張メソッドにラムダを渡したとき、宣言の順番で結果が変わらなくなりました¶

    extension で同じ名前のメソッドを複数宣言した場合、ラムダ引数で選ばれる多重定義は、宣言の順番によらず同じになりました。 以前は、最初または最後に宣言された多重定義が実行されることがよくありました。 全体として、次のように変わります。

    • コンパイルできていた呼び出しで、別の多重定義が実行されることがあります。 クラスのメソッドが選ぶもの（下記の 1 点を除く）です。主に、引数の型を書いていないラムダが対象です。
    • コンパイルできていた呼び出しが E0006 になることがあります。 2 つの多重定義が同じ程度に当てはまる場合です。
    • 以前の多重定義を保つには: ラムダの引数に型を書く、ほかの引数を as で渡す（5 as Object、2 as Double）、ラムダを型付きの値として渡す、またはどちらかのメソッド名を変えてください。

    例:

    • 対象: クラスの型変数で宣言されたメソッド引数です。関数値への f(null) と f.call(null)、List と Map の add/set/put、Java の関数型インタフェースの apply、自分で書いた総称クラスのメソッド（Box[Int].put(null)）が該当します。そのような型として書いたリストやマップのリテラルの中の null の要素も該当します（val zs: List[Int] = [5, null]、val m: Map[String, Int] = ["b": null]）。同じ枠に届くほかの書き方も該当します（#2991）。コンストラクタ（new Box[Int](null)、new R[Int](null)）、添字への代入（xs[0] = null、m["b"] = null）です。
    • 直し方: null を格納するつもりなら、型引数を null 許容にしてください。List[Int?]、Map[String, Int?]、(Int?) -> T です。読み出した値は Int? になるので、そこで null を扱います（?: か !!）。そうでなければ、null ではなく実際の値を渡してください。
    • onion migrate の規則はありません: 直し方は、宣言する型を変えるか、渡す値を変えるかのどちらかです。どちらが正しいかは、書いた人にしか分かりません。

    protected なメソッドは、どの呼び方でも同じようにアクセス検査されるようになりました¶

    名前付き引数を渡すメソッド呼び出しと、型を書かないラムダ引数を渡すメソッド呼び出し（a.lam((x) -> x + 1)、a.lam { x -> x + 1 }）も、すべての引数を位置で渡す呼び出しと同じアクセス検査を受けるようになりました (#2916)。 そのため、無関係なクラスからこの方法で protected なメソッドを呼ぶことはできなくなりました。 これは、上のコンストラクタの変更のメソッド版です。

    class A {
public:
  def this() { }
protected:
  def pim(a: Int, b: Int = 2): Int = a + b
}
println(new A().pim(b = 3, a = 7))   // 以前: 10 と表示された。今: E0013
println(new A().pim(7, 3))           // 以前も今も E0013
    • 表示されるもの: 呼び出しの位置で E0013 method A.pim(Int, Int) is not accessible from class ... になります。
    • これまでどおり動くもの: A の中や、A のサブクラスからの同じ呼び出しです。
    • 直し方: メソッドを public: の下に移すか、サブクラスから呼んでください。
    • onion migrate の規則はありません: メソッドのアクセスを広げるかどうかは、書いた人にしか決められない設計上の判断です。そのため、ヒントが直し方を示します。

    Yaml::stringify は Yaml::parse が読み戻せるものだけを書くようになりました¶

    Yaml::stringify は、スカラーのリスト、空の Map の要素、NaN を書いていました。その一部は他の YAML ツールなら読めます。しかし Yaml::parse では読み戻せませんでした。今は、入れ子の Map と同じく、Yaml::stringify が例外を投げます (#2806)。

    import { onion.Yaml; onion.Json }
Yaml::stringify(["apple", "banana"])   // 以前: "- apple\n- banana\n"。今: 例外
Json::stringify(["apple", "banana"])   // ["apple","banana"]。JSON は YAML 1.2 としても正しい
Yaml::stringify(["apple", "banana"].map { x -> ["v": x] })   // - v: apple ...
    • 表示されるもの: 実行時の IllegalArgumentException です。メッセージが問題を示し、直し方を提案します。
    • 対象:
    • Map でないリストの要素: String、数値、null、List
    • 空の Map の要素 ([[:]])
    • 値のどこかにある、NaN または無限大の Double や Float
    • NaN または無限大の成分を持つレコードの toYaml (derive!(Yaml)) と、shape ... = yaml の print
    • これまでどおり動くもの: フラットな Map と、空でないフラットな Map のリストです。どちらも以前と同じように書かれます。
    • 直し方:
    • スカラーのリストには Json::stringify を使ってください (YAML 1.2 のツールは JSON を読めます)。または、各要素を Map で包んでください: xs.map { x -> ["v": x] }。
    • 空の Map はリストから除いてください。
    • 書く前に、NaN や無限大を自分で選んだ値 (null や番兵値) に置き換えてください。
    • onion migrate の規則はありません: 拒否される入力はソースの書き方ではなく実行時の値です。そのため、書き換えでは見つけられません。代わりに例外のメッセージが直し方を示します。

    Args の intOption は Int でない値を拒否するようになりました¶

    opts.intOption(name, default) は、値が整数でないときに既定値を返していました。そのため、--count 10O（英字の O）のような打ち間違いも、何事もなかったように動いていました。今は例外を投げます。自動 CLI（def main(count: Int = 3)）は、同じ入力をすでに拒否していました（#2881）。

    • 変わらないもの: オプションがなければ、これまでどおり既定値を返します。正しい値（--count 7、--count -5）もこれまでどおり読み取れます。
    • 以前の結果を保つには: 例外を捕まえて既定値を使います。 val n = try { opts.intOption("count", 3) } catch e: IllegalArgumentException { 3 }
    • onion migrate の規則はありません: 以前の動作は、実行時のエラーを握りつぶしていただけです。ソースには書き換えるものがありません。不正な値でプログラムを止めるべきかどうかは、書いた人にしか分かりません。

    self は this になりました¶

    self は this の別の書き方でした。Onion は書き方を this の一つにします（RFC #2788）。

    // 以前
def this(name: String) { self.name = name }
def greet(): String = "Hi, #{self.name}"

// 今
def this(name: String) { this.name = name }
def greet(): String = "Hi, #{this.name}"
    • 表示されるもの: すべての self で、一度に E0117:selfは廃止されました。thisと書いてください。 が出ます。static なコードでは E0050 の代わりに出ます。
    • 予約語のままです: self は自由な名前にはなりません。`self` と書いたフィールドはこれまでどおり使えます。
    • プロジェクト全体を更新するには: onion migrate src/ tests/ を実行します。コード中の self と、文字列の #{...} の中の self をすべて書き換えます。コメント、文字列の地の文、\#{self}、`self` はそのままです。

    override は、? の違いを除いて基底メソッドと同じ型でなければならなくなりました¶

    基底が Int のところを JInteger にした override や、基底の戻り値が Int のところを Int? にした override は、何もオーバーライドしていませんでした。 新しいオーバーロードとしてコンパイルされ、基底型を通した呼び出しは基底のメソッドを実行していました。 今は E0068 になります (#2896)。

    class Base {
public:
  def this {}
  def dec(k: Int): void { println("Base") }
}
class Up extends Base {
public:
  def this {}
  override def dec(k: JInteger): void { println("Up") }   // 以前: コンパイルできた。今: E0068
}
val b: Base = new Up(); b.dec(1)                           // 以前: Base と表示された
    • 表示されるもの: E0068 メソッド dec(JInteger) に override が付いていますが、... と、基底のシグネチャ（dec(Int): void）です。
    • これまでどおり動くもの: dec(k: Int) に対する override def dec(k: Int?) は、パラメータが ? だけ違うので、今は本当にオーバーライドします。ジェネリックな上位型（G[JInteger]）を通したボックス型のパラメータもオーバーライドします。
    • 直し方: オーバーライドするなら、基底の型（dec(k: Int) か dec(k: Int?)）を書いてください。別のオーバーロードとして残すなら、override を外し、? 以外でも違うパラメータ型にするか、別の名前にしてください。
    • onion migrate の規則はありません: オーバーライドのつもりかオーバーロードのつもりかは、書いた人にしか決められません。二つの直し方は別のコードを実行します。そのため、エラーが基底のシグネチャを示します。

    パラメータが基底メソッドと ? だけ違う メソッドは、override の有無にかかわらず、今は同じメソッドです。

    • 以前: override のない def dec(k: Int?): void は、基底の dec(k: Int): void とは別のオーバーロードでした。Base を通した b.dec(1) は基底を実行していました。戻り値が参照型（String）なら、同じメソッドがすでにオーバーライドしていました。つまり override は、参照型の戻り値では何も変えず、void やプリミティブの戻り値では結果を決めていました。
    • 今: どの戻り値型でもオーバーライドします。override は、型が完全に同じときと同じく検査だけをします。どのメソッドが実行されるかは決めません。override がなければ、コンパイラは W0029 で警告します（'dec(Int?)' overrides 'dec(Int): void' of Base ...）。基底メソッドが final なら、型が完全に同じときと同じく E0039 です（Thread のサブクラスの setDaemon(on: Boolean?) も含みます）。
    • 逆向きは変わりません: 基底の f(k: Int?): void に対する自前の f(k: Int): void は、オーバーロードのままです。そのため、Base を通した null は基底のメソッドに届きます。override を付けると E0068 です。オーバーライドするなら、パラメータを Int? にしてください。
    • W0029 を消すには: 基底のメソッドを置き換えるつもりなら、override を付けてください。
    • 別のオーバーロードとして残すには: メソッドの名前を変えてください（decOrSkip(k: Int?)）。onion migrate の規則はありません。基底のメソッドを置き換えるつもりだったかどうかは、書いた人にしか分かりません。

    プリミティブ型のパラメータは、ボックス型の抽象メソッドを実装しなくなりました¶

    総称型でないインターフェースや抽象クラスが JInteger を取るところで、Int を取るクラスのメソッドが実装として受け入れられていました（逆も同じです）。 二つをつなぐブリッジはないので、上位型を通した呼び出しは AbstractMethodError を投げていました。 今は、そのクラスが E0037 になります (#2922)。

    interface I { def n(x: JInteger): String }
class C conforms I {            // 以前: コンパイルできた。今: E0037
public:
  def this {}
  def n(x: Int): String = "int " + x
}
val i: I = new C; println(i.n(4))   // 以前: AbstractMethodError
    • 表示されるもの: E0037 クラス C は抽象メソッド n(java.lang.Integer) を実装するか、... と、n(Int) はこのメソッドを実装しません。... 実装するには n(JInteger) と宣言してください。 です。
    • これまでどおり動くもの: 総称型の上位型（n(x: T) を持つ G[JInteger]）では、n(x: Int) にブリッジが作られます。? だけ違うパラメータ（n(x: Int) に対する n(x: Int?)）も実装になります。
    • 直し方: 上位型のパラメータ型を書いてください（def n(x: JInteger)）。ほかのコードが Int のメソッドを呼んでいるなら、並べて残してかまいません。
    • onion migrate の規則はありません: これに当たるプログラムは、上位型を通した呼び出しを一度も実行できていません。また、二つのメソッドのどちらを実行すべきかは、書いた人にしか分かりません。そのため、ヒントが正しい書き方を示します。

    OnionMath::randomInt は削除されました。Rand::nextInt を使ってください¶

    範囲内のランダムな Int を得る方法が二つあり、上限の扱いが逆でした（#3069）。 残るのは Rand::nextInt(min, max) です。max は含まれません。a..<b、Java、Kotlin と同じです。

    val die = OnionMath::randomInt(1, 6)   // 以前: 1から6。現在: E0005
val die = Rand::nextInt(1, 7)          // 1から6
    • 表示されるもの: E0005 と、Rand::nextInt(min, max + 1) を示すヒントです。
    • 変わらないもの: Rand::nextInt(min, max) と OnionMath::random() です。
    • onion migrate が書き換えます。 Rand::nextInt(min, max + 1) と書くので、以前の呼び出しが返せた値はすべて出ます。
    • OnionMath::randomInt(1, 6) は Rand::nextInt(1, 7) になります。
    • OnionMath::randomInt(0, xs.size - 1) は Rand::nextInt(0, xs.size) になります。
    • OnionMath::randomInt(a, b) は Rand::nextInt(a, b + 1) になります。
    • "#{...}" の中の呼び出しと、別の呼び出しの引数の中の呼び出しも書き換えます。
    • インポート経由の呼び出しも書き換えます。import { onion.OnionMath::* } の後の randomInt(1, 6) や、import { onion.OnionMath as OM; } の後の OM::randomInt(1, 6) です。インポート自体はそのままでもコンパイルできるので、書き換えません。
    • ファイル自身、または一緒に渡したファイルに独自の Rand（クラス、インポート、変数）があるときは、onion.Rand::nextInt と書きます。呼び出しが Onion の Rand を指したままになります。
    • 書き換えるのは、コンパイラがエラーを報告した呼び出しだけです。 コンパイルできる randomInt はあなた自身のもの（OnionMath という名前の自作クラスや、継承したメソッド）なので、そのまま残します。
    • + 1 を付ける max: Int.MAX_VALUE より小さい数字そのもの（6）か、変数、引数、フィールド、呼び出しを読む max（n、xs.size、Math::abs(n)）です。
    • それ以外の定数の max は知らせるだけです。手で直してください。 2147483647 や、定数の式（1 << 4、Integer::MAX_VALUE）が該当します。migrate はファイルをそのまま残します。Rand::nextInt(min, (max) + 1) と書いてから、もう一度 migrate を実行してください。max が Int.MAX_VALUE のときは、代わりに Rand::nextInt(min - 1, max) + 1 と書いてください。
    • 独自の randomInt も持つファイルの、修飾なしの randomInt(a, b) はどちらを指すかわからないので、migrate は知らせるだけで書き換えません。
    • import { onion.OnionMath::* } のないファイルの randomInt(a, b) は削除されたメソッドではないので、migrate は書き換えません。ヒントが手で直す書き換えを示します。
    • 変数に入った max は確認してください。 migrate にはその値がわかりません。実行時に Int.MAX_VALUE になりうるなら、そこで max + 1 が桁あふれし、呼び出しは IllegalArgumentException を投げます。その場合は Rand::nextInt(min - 1, max) + 1 と書いてください。
    • Rand::nextInt() で置き換えられるのは、min が Int.MIN_VALUE で max が Int.MAX_VALUE の呼び出しだけです。 負の数も含むあらゆる Int を返すので、randomInt(0, Int.MAX_VALUE) の代わりにはなりません。
    • プログラムは一つずつ migrate してください。 無関係なスクリプトを一緒に渡すと、互いのエラーが隠れることがあります。その場合、呼び出しは書き換えられずに残ります。

    総称メソッドの多重定義が、Java と同じように通常の多重定義と競合するようになりました¶

    通常のクラスは、実装しているインタフェースを通じて総称メソッドの引数に当てはまるようになりました（#2845）。 String は Comparable[String] なので、g[T](c: Comparable[T]) は g("a") に当てはまります。 通常の多重定義も当てはまる場合は、Java の規則でどちらかを選びます。

    g(CharSequence)、g[T](Comparable[T]) g("a") charseq E0006 g("a" as CharSequence)
    f(Serializable)、f[T](Comparable[T]) f("a") serializable E0006 f("a" as Serializable)
    f(Object)、f[T](Comparable[T]) f("a") object generic f("a" as Object)

    • ヒントが示す引数: 変換すると総称メソッドが当てはまらなくなる、最初の引数です（log("t", "m") では第 2 引数）。 可変長引数は要素の型に変換します。g(c: CharSequence...) なら g("a" as CharSequence) です。
    • 今までどおり動くもの: 引数のクラスが総称メソッドの引数のインタフェースを実装していない呼び出しと、 どちらか一方の多重定義しか当てはまらない呼び出しです。
    • onion migrate の規則はありません: 影響を受ける呼び出しを見つけるには多重定義の解決が必要です。 また、どの多重定義を意図したかは書いた人にしか分かりません。代わりにヒントが as を示します。

    f(x) と f(xs...) に配列を渡すと、Java と同じメソッドが選ばれるようになりました (#2955)¶

IO::println(JList::of[String[]](sa).size())   // 以前も現在も 1

    総称レコードのコピーが型引数を保つようになりました (#3101)¶

    以前は、総称レコードの copy(..) が裸の型変数のレコードを返していました。 そのため、コピーから読んだ要素は型 A でした。 現在のコピーは、this と同じく受け手自身の型を持ちます。

    record P[A, B](x: A, y: B)
val q = new P[String, Int]("s", 1).copy(y = 2)
val s: String = q.x()   // 以前: E0000。現在: s
    プログラム 以前 現在 以前の結果を保つには
    f(o: Object) と f(s: String) がある f(q.x()) f(Object) f(String) f(q.x() as Object)
    p: P[String, Int] での val r: P[Object, Int] = p.copy(y = 3) コンパイルできた E0000 new P[Object, Int](p.x(), 3)
    take(r: P[Object, Int]) がある take(p.copy()) コンパイルできた E0005 take(new P[Object, Int](p.x(), p.y()))
    • 表示されるもの: E0000（type P[Object, Int] is expected, but type P[String, Int] is used）、 引数なら E0005 です。多重定義の呼び出しでは何も表示されず、別のメソッドが実行されます。
    • 代入が拒否される理由: 型引数は不変（invariant: 型引数が違えば別の型）です。 copy を使わない val r: P[Object, Int] = p も、もともと E0000 でした。コピーも同じ規則に従います。
    • 今までどおり動くもの: バイトコード、総称でないレコード、利用者が定義した copy メソッドです。
    • onion migrate の規則はありません: 影響を受ける呼び出しを見つけるには多重定義の解決が必要です。 また、どのメソッドのつもりかは書いた人にしか分かりません。表に各書き換えを示します。

    型引数の違う分岐が、期待される型で検査されるようになりました (#3241)¶

    同じ総称クラスで型引数だけが違う二つの分岐は、原型（raw: 型引数のないクラス）に合流します。 以前は、原型の値がどの期待される型にも合っていました。 現在は、if・select・try に型引数つきの期待される型があれば、各分岐をその型で検査します。

    val other: Option[String] = Option::some("str")
val tail: Option[Int] = Option::none()
val c: Option[Int] = if b { other } else { tail }   // 以前: コンパイルできた。現在: `other` で E0000
    プログラム 以前 現在 コンパイルを通すには
    val c: Option[Int] = if b { other } else { tail } コンパイルでき、c.get() + 1 が ClassCastException を投げた E0000 分岐を期待される型にそろえるか、Object のような広い型にする
    def f(b: Boolean): Option[Int] = if b { other } else { tail } コンパイルできた E0000 同上
    • 表示されるもの: E0000（type Option[Int] is expected, but type Option[String] is used）です。 キャレットは型の合わない分岐を指します。
    • 今までどおり動くもの: 期待される型に合う分岐、Object のような期待される型、 期待される型のない合流です（val c = if b { other } else { tail } は今も原型の Option です）。
    • onion migrate の規則はありません: プログラムが間違った型の値を持っています。 どの分岐が間違いかは書いた人にしか分かりません。エラーがその分岐を指します。
