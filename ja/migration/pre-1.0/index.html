    1.0 への移行¶

    Onion は、まだ影響が小さいうちに、1.0 の前に構文と API を整理しています。 互換性を壊す変更を、コードの直し方と一緒にここにまとめます。

    1.0 以降は互換性を約束します。1.x でコンパイルできるプログラムは、 その後の 1.x でもコンパイルでき、意味も変わりません。

    ret は yield になりました¶

    do ブロックの最後の値は yield で書きます。

    // 以前
val sum = do[Option] { a <- getA(); b <- getB(); ret a + b }

// 現在
val sum = do[Option] { a <- getA(); b <- getB(); yield a + b }
    • 変わったこと: yield は予約語になりました。ret は普通の識別子に戻りました。
    • 表示されるもの: 古いコードでは「ローカル変数 ret が見つかりません」と表示され、yield を使うようヒントが出ます。
    • yield という名前の Java メソッド: バッククォートで呼び出します（例: Thread::`yield`()）。
    • プロジェクト全体を書き換える: onion migrate src/ tests/（ファイルやディレクトリを任意に指定できます）。 書き換えるのは do ブロックの ret だけです。ret という名前の変数・文字列・コメントは変えません。

    2147483648 の直前には - が必要になりました¶

    リテラル 2147483648（と 9223372036854775808L）は、-2147483648 のように単項 - のオペランドそのものである場合だけ有効です。 それ以外の場所では、以前は黙って最小値に化けていました。

    // 以前: コンパイルでき、意外な値になっていた
val a = 1 - 2147483648          // -2147483647（ラップアラウンドによる）
val b = -2147483648 as Long     // 2147483648: `as` は `-` より強く結合する
val c = -2147483648 / 2         // 1073741824: `/` は `-` より強く結合する

// 現在
val a = 1 - 2147483648L         // または 1L - 2147483648L
val b = -2147483648L            // または (-2147483648) as Long
val c = (-2147483648) / 2       // -1073741824
    • 変わったこと: 最小値の絶対値は、トークンではなく、それを符号反転する場所で検査します。
    • 表示されるもの: リテラルの位置に「整数リテラルがIntの範囲(-2147483648..2147483647)を超えています -- Long型リテラルにするには末尾にLを付けてください。」と表示されます（L 付きなら Long の範囲のメッセージです）。
    • 引き続き使えるもの: -2147483648、x + -2147483648、3 * -2147483648、-9223372036854775808L、0x80000000 のような 16 進数・2 進数のビットパターン。

    10進数の B/S リテラルは符号付きの範囲に収める必要があります¶

    10進数の Byte リテラルは -128..127、10進数の Short リテラルは -32768..32767 の範囲になりました。 Java と同じです。以前は、範囲外の値が黙って桁あふれしていました。

    // 以前: コンパイルが通り、意外な値になる
val mask: Byte = 255B           // -1
val port: Short = 40000S        // -25536
val n = -128B as Int            // 128: `as` は `-` より強く結合する

// 現在
val mask: Byte = 0b11111111B    // -1。ビットパターンとして書く
val port: Int = 40000           // Short には 40000 は入らない
val n = (-128B) as Int          // -128
    • 変更点: 2147483648 と同じく、128B と 32768S は - のオペランドそのものである場合だけ有効です。
    • 表示されるエラー: リテラルの位置に「整数リテラルがByteの範囲(-128..127、またはビットパターンとして0b11111111まで)を超えています -- ...」が出ます（S サフィックスなら Short）。
    • 引き続き使えるもの: 0b11111111B のような2進数のビットパターンと、0xFFFFS のように S を付けた16進数。
    • 16進数と B: 16進数リテラルの B は数字であり、接尾辞ではありません。0xAB は Int の 171、0xFFB は Int の 4091 です。Byte にしたいときは 0b11111111B か -1B と書いてください。
    • そのようなリテラルが Byte に収まらなくなった箇所（val x: Byte = 0xFFB、Byte 引数への f(0xFFB)）では、エラーにその理由を示すヒントが付きます。
    • まだ収まる箇所では何も報告されず、値だけが変わります。bs[0] = 0x1B は 27 を格納し（以前は 1）、val y = 0x7FB は 2043 です（以前は Byte の 127）。末尾が B の16進数リテラル（0x...B）をコードから検索してください。

    config ファイルの引用符付き String は、引用符を外して読むようになりました¶

    shape name = config のレコードは、二重引用符で囲まれた String の値を、引用された文字列として読みます。 これで、前後の空白を持つ値も print と parse を往復できます。

    # 以前: 引用符も値の一部だった
name = "Alice"          # "Alice" と読む（7 文字）

# 現在
name = "Alice"          # Alice と読む（5 文字）
name = "  Alice  "      #   Alice   と読む（空白を保つ）
name =   Alice          # Alice と読む（引用符のない値はこれまでどおり trim）
name = "\"Alice\""      # "Alice" と読む（引用符を文字として残す書き方）
    • 変わったこと: 引用符の中では、\" が引用符、\\ がバックスラッシュです。 それ以外のバックスラッシュはそのまま残るので、"C:\temp" は C:\temp と読みます。
    • 表示されるもの: 引用符を文字として使っていたファイルもそのまま parse に成功します。 そのため、エラーもヒントも出ません。値の外側の引用符が消えるだけです。 設定ファイルの中から " で始まる値を探してください。 閉じる " のない値や、中に裸の " がある値（"a" and "b"）は、行番号付きの Defect になります。
    • 対象は String 成分だけです: Int や Boolean などのスカラーは、これまでどおりに読みます。

    型 T の場所には T しか入らなくなりました¶

    ジェネリッククラスの中で、型パラメータ T で型付けしたフィールド・ローカル変数・引数への代入と初期化、 : T と宣言したメソッドの戻り値には、型 T の値だけが入ります。Java と同じです。 以前は T の上限に合う値なら何でも入り、次に読んだところで ClassCastException が出ていました。

    class S[T, U] {
  var t: T
  var u: U
public:
  def this(x: T, y: U) { t = x; u = y }

  // 以前: コンパイルが通り、new S[String, Integer]("a", 1) で t を次に読むと例外になる
  def f(): void { t = u }

  // 現在: 値が本当に T なら、検査なしのキャストを自分で書く
  def g(): void { t = (u as T) }
}
    • 変わったこと: 無関係な型変数（U）、上限の型（Object、CharSequence）、 具体的な型（"x"）の値は、T の場所に入らなくなりました。
    • 表示されるエラー: 値の位置に「E0000 型 T が期待されている箇所に、型 U を使用しました。」が出ます。
    • 引き続き使えるもの: T の値、T を上限に持つ型変数（[T, U extends T] での t = u）、null、 raw な Java の受け手に対する Java メソッドの引数（(o as ArrayList).add(u)）。 そこから読み戻した値（t = (o as ArrayList).get(0)）は T ではないので、キャストが必要です。
    • 同じ名前 T の型パラメータが二つある場合: class K[T] の中のメソッドの [T] は、別の T です。 このときエラーにはその旨のヒントが付きます。クラスの T を使うなら、メソッドの [T] を外してください。
    • 呼び出し: 継承したメソッド（Mid[U] extends Box[U] の中の set(o)）と、 型変数で型付けした受け手（xs: List[T] に対する xs.add(o)、b: Box[T] に対する b.set(o)）では、引数も検査します。
    • T? の場所: T の場所に入るものに加えて、null と T? が入ります。 そのため o: T? への o = u、o = uo（uo: U?）、o = "x" も E0000 になります（#2332）。 T? 型のコンストラクタ引数（def this(x: T?) に対する new Box[T](u)）は、T 型の引数と同じく E0021 になります。
    • 添字代入とリテラル: List[T] や Map[K, T] への xs[0] = u、m["k"] = u は、xs.set(0, u) と同じく E0000 になります（#2332）。 List[T] や Map[K, T] として使うリテラル [u]、[t, u]、["k": u] も E0000 です。 エラーにはリテラルの型（List[U]、型が混ざる場合は List[Object?]）が出ます。 List[Object] が期待される場所では、[t, u] は今も使えます。値が本当に T なら [(u as T)] と書いてください。
    • 継承したメンバーは U になりました: class Mid[U] extends Box[U] の中で、継承した get(): T は U です（以前は Object）。 U は null になりうるので、get().toString() は E0057 になります。Box の中では以前からそうでした。 get()?.toString() や get() ?: 代わりの値 と書くか、class Mid[U extends Object] のように null でない上限を付けてください。 Java のスーパークラスでも同じです。class MyList[T] extends ArrayList[T] の中の get(0).toString() も E0057 になります。
    • this は Mid[U] です: class Mid[U] の中の this は U を保ちます。 val me = this、id(this)、[this]、() -> this を通しても同じです。 そのため same(this) は継承した same(o: Box[T]) に渡せ、me.get() は U です（以前は raw な Mid で、me.get() は Object でした）。
    • 型引数が異なる分岐: if b { [t] } else { [u] } は raw な List になります。 Object が期待される場所ではコンパイルできます。List[T] が期待される場所では、[u] の分岐が E0000 になります。
    • onion migrate の書き換え規則はありません（意図的です）: 機械的にできる書き換えは (u as T) の挿入だけです。 それでは、この検査が見つけるバグをそのまま隠してしまいます。エラーを一つずつ読んで判断してください。

    空の [] / [:] は、隣の要素の型になりました¶

    リストリテラル、またはマップリテラルの値に空の [] / [:] があると、他の要素が揃っている型として扱います。 以前は、リテラル全体が Object に広がっていました。

    val adj = [[1, 2], []]

// 以前: List[Object] なので、adj[1].add(5) は E0005 で、次の行はコンパイルできた
adj.add("header")

// 現在: List[List[Int]] なので、adj[1].add(5) はコンパイルでき、次の行は E0005
adj.add("header")

// 以前の型を保つには、型を注釈する
val xs: List[Object] = [[1, 2], []]
    • 変わったこと: 空のリテラルは、隣の要素の後に、その型で型付けされます。要素の評価順は、これまでどおりソースの順です。
    • 表示されるもの: 異なる種類の要素を混ぜたコードや、List[Object] の引数に渡したコードで、List[List[Int]].add(String)（または Map[String, List[Int]].set(...)）を示す E0005 が出ます。
    • そのまま動くもの: 明示した型注釈が優先されます。型の分かる隣の要素がないリテラル（[[], []]）は、これまでどおりです。

    多重定義された拡張メソッドにラムダを渡したとき、宣言の順番で結果が変わらなくなりました¶

    extension で同じ名前のメソッドを複数宣言した場合、ラムダ引数で選ばれる多重定義は、宣言の順番によらず同じになりました。 以前は、最初または最後に宣言された多重定義が実行されることがよくありました。 全体として、次のように変わります。

    • コンパイルできていた呼び出しで、別の多重定義が実行されることがあります。 クラスのメソッドが選ぶもの（下記の 1 点を除く）です。主に、引数の型を書いていないラムダが対象です。
    • コンパイルできていた呼び出しが E0006 になることがあります。 2 つの多重定義が同じ程度に当てはまる場合です。
    • 以前の多重定義を保つには: ラムダの引数に型を書く、ほかの引数を as で渡す（5 as Object、2 as Double）、ラムダを型付きの値として渡す、またはどちらかのメソッド名を変えてください。

    例:

    多重定義 呼び出し 以前 現在 以前の結果を保つには
    Object 上の z(f: (Object) -> void)、String 上の z(o: Object) "abc".z((x: Object) -> …) String の z(Object) E0006 どちらかのメソッド名を変える
    c(n: Long, g: (Long) -> Long)、c(n: Object, g: (Long) -> Long) "a".c(5, (x: Long) -> x * 2L) 順番により obj または long:10 E0006 long:10 には "a".c(5L, …)、obj には "a".c(5 as Object, …)
    k(s: Supplier[String])、k(c: Callable[String]) "a".k { "v" } 順番により call または sup E0006 call には val c: Callable[String] = () -> "v" として "a".k(c)、sup には同様に val s: Supplier[String]
    String 上の f(o: Object, g)、CharSequence 上の f(s: String, g) "a".f("q", (x: Int) -> x) strobj1 E0006 "a".f("q" as Object, …)
    outer(f: (Int) -> Int)、outer(f: Function[String, String])（import { java.util.function.Function }） "a".outer { p -> ((q: Int) -> p).call(1) } 順番により os:s または oi:1 oi:1 val g: Function[String, String] = (p: String) -> … として "a".outer(g)
    r(f: () -> void)、r(o: Object) "a".r { IO::print("") } 順番により obj または fn fn val h: () -> void = () -> … として "a".r(h as Object)
    m(n: Int, f: (Int) -> Int)、m(n: Object, f: (Object) -> Object) "a".m(1, { x -> x }) 順番により obj:1 または int:1 int:1 "a".m(1 as Object, { x -> x })
    k(n: Int, f: (Int) -> Int): Int、k(n: Double, f: (Double) -> Double): Double "a".k(2, { x -> x * 2 }) 4.0（Double のほう） 4 "a".k(2, (x: Double) -> x * 2.0)
    run(r: Runnable)、run(c: Callable[Object]) "a".run { IO::print("") } callable:null runnable 型付きの Callable[Object] の値を渡す
    • 変わったこと: ラムダが当てはまる多重定義を、issue #2447 に書かれた 1 つの規則で順位付けします。 これはクラスのメソッドの規則に、1 点を加えたものです。関数型の引数は、Function や Comparator のような SAM インターフェース（抽象メソッドが 1 つのインターフェース）より優先されます（outer の行）。 クラスのメソッドでは、ここはまだ E0006 になります。クラスを同じ規則にそろえる作業は #2472 で扱います。
    • 表示されるもの: E0006（2 つのメソッドのどちらにも当てはまるという意味のエラー）が出ます。最後の列の直し方を示すヒントが付きます。
    • そのまま動くもの: 当てはまる多重定義が 1 つだけの呼び出しと、ラムダ引数のない呼び出しです。

    任意の Iterable に対する map / filter は List を返すようになりました¶

    範囲、map.values()、その他 List でも Set でもない Iterable に対する map と filter は、List を返すようになりました。 以前は、結果はすでにリストでしたが、型は Iterable でした。

    val evens = (1..10).filter { x -> x % 2 == 0 }
evens.size                         // 以前: E0004。現在: 5

var xs = (1..3).map { x -> x + 1 }
xs = new java.util.TreeSet[Int]()  // 以前: コンパイルできた。現在: E0000

// どの Iterable も保持できる変数にするには、型を宣言する
var ys: Iterable[Int] = (1..3).map { x -> x + 1 }
ys = new java.util.TreeSet[Int]()
    • 変わったこと: Iterables::map(Iterable, f) と Iterables::filter(Iterable, p) は List[T] を返します。リストやセット自身の map / filter は変わりません。
    • 表示されるもの: E0000（型が合わないという意味のエラー）が出ます。var xs: Iterable[Int] = ... と宣言するよう促すヒントが付きます。
    • 動作が変わるもの: Iterable と List の両方に多重定義や拡張メソッドがある場合、結果に対する呼び出しは List の方を選びます。以前の選択を保つには、どちらかの名前を変えてください。
    • 再コンパイルが必要なもの: 古い onion.jar に対してコンパイルしたクラスがこれらのメソッドを呼ぶと、再コンパイルするまで NoSuchMethodError を投げます。
    • そのまま動くもの: このようなパイプラインの後の .toList() は、これまでどおり動きます。結果は Iterable の引数や変数にもそのまま渡せます。

    example と law は契約の述語になりました¶

    ビルド時に実行される検査は、Boolean を返して ensures result と述べる static def で書きます。 引数のある述語は、law と同じようにサンプリングして実行されます。

    // Before
record Pt(x: Int, y: Int) from re"(-?\d+),(-?\d+)" {
  law roundtrip(p: Pt) { Pt::parse(Pt::format(p)) == p }
  example { Pt::parse("3,4") == new Pt(3, 4) }
}

// Now
record Pt(x: Int, y: Int) from re"(-?\d+),(-?\d+)" {
public:
  static def roundtrip(p: Pt): Boolean
    ensures result
    = Pt::parse(Pt::format(p)) == p
  static def parsesThreeFour(): Boolean
    ensures result
    = Pt::parse("3,4") == new Pt(3, 4)
}
    • 変わったこと: example と law を削除しました。トップレベルでは def name(): Boolean ensures result = expr と書きます（static は付けません）。複数文の本体は、最後に return を置くブロックにします。
    • 見えるもの: 偽の述語は E0113 になります。サンプルを作れない引数の型も、黙って通さず E0113 です。 --contracts は既定で有効（check）です。
    • シードとサンプル数: --law-seed と --law-samples は --contract-seed と --contract-samples になり、--no-check-laws は無くなりました（--contracts off を使います）。
    • onion.Shape: 実装するクラスのファイルに述語は不要になりました（E0080 は廃止です）。
    • プロジェクト全体の更新: onion migrate src/ は、law と example をこの形に書き換えます。
    • 式1つの本体は = expr になります。それより長い本体はブロックのまま残し、最後の文の前に return を置きます。
    • 名前のない example は example1、example2、... と名付けます。名前は自由に変えてかまいません。
    • 書き換えてもコンパイルできないファイルは元のまま残し、その行を表示します。

    invariant や history が名指すフィールドは this を通してしか書けなくなりました¶

    契約はプレビュー機能です（RFC #2557）。クラスの invariant や history が名指すフィールドは、 そのクラス自身のコードから this を通してだけ書けます。ほかのオブジェクトを通した書き込みは E0110 です。

    class Clock {
public:
  var t: Int
  history t >= old(t)
  def this { t = 0 }
  def this(start: Int) { t = start }
  def advanceTo(k: Int): void { if k > t { t = k } }
}

// Before: compiled. Now: E0110 at `c`
//   val c = new Clock(); c.t = 5
// Now: pass the value to a constructor
val c = new Clock(5)

// Before: compiled. Now: E0110 at `o`
//   def sync(o: Clock): void { o.t = 9 }
// Now: call a method of that object; its own writes are checked
def sync(o: Clock): void { o.advanceTo(9) }
sync(c)
println(c.t)   // 9
    • 変わったこと: 各オブジェクトは自分の invariant と history を持ち、呼び出し1回ごとに検査されます。 そのオブジェクトのメソッドの外からの書き込みは、この検査では追えません。
    • 見えるもの: E0110（契約フィールドへの書き込みを禁じるエラー）が出ます。キャレットは受け手（o、c、cs[0]）を指します。 メッセージは、そのオブジェクトのメソッドを呼ぶか、コンストラクタで値を設定するよう促します。
    • そのまま動くもの: クラス自身のメソッドでの t = v、this.t = v、self.t = v、t++、t += 1 です。ラムダの中でも同じです。 o.t を読むことは、どこからでもできます。
    • onion migrate の書き換え規則はありません（意図的です）: 直すには受け手のクラスにメソッドかコンストラクタを足します。 どれが合うかは設計の判断です。

    tool の requires が、本体の実行内容をより多く数えるようになりました¶

    onionc は tool の requires { ... } を、本体が持つ効果（外の世界への作用）と照らし合わせます。 これまで見落としていた4つを数えるようになりました。 見落としに頼っていた tool は E0077（requires に足りない効果）か E0078（使われない能力）になります。

    class Base {
public:
  def this {}
  def run(): Int = 1
}
class Loud extends Base {
public:
  def this {}
  override def run(): Int { IO::println("loud"); return 2 }
}

// Before: compiled. Now: E0077 at `b.run()`, "calling Loud::run"
//   tool go(): Int { val b: Base = new Base(); return b.run() }
// Now: declare what an override can do
tool go(): Int requires { console } {
  val b: Base = new Base()
  return b.run()
}
    tool がすること 以前 今
    プログラムのクラスがオーバーライドするメソッドを呼ぶ（上の b.run()） 呼んだメソッドだけを数えた プログラム中のオーバーライドもすべて数える（E0077）
    static 初期化子に効果があるクラスを使う 数えなかった 数える（E0077）
    R がプログラムのクラスである try (val r = new R()) { } close() を数えなかった R::close を数える（E0077）
    プログラムのジェネリッククラスの new Box[String]() unknown コンストラクタ自身の効果。これのためだけの unknown は E0078
    • 見えるもの: E0077 は呼び出しと、足すべき能力を示します。E0078 は、外すべき能力を示します。
    • 影響しないもの: 渡したオブジェクトに対してライブラリが呼び返すかもしれないもの（list.add(item) と Item::toString）は数えません。 これを数えるのは、ビルドが契約の述語を実行してよいかの検査だけです。
    • onion migrate の書き換え規則はありません（意図的です）: 直し方は、呼ばれるコードが何をするかで決まります。 エラーがそれぞれ直し方を示します。その能力を足すか、使われない能力を外してください。

    hashCode / toString / getClass という名前の成分は、そのメソッドの型を変えられなくなりました¶

    record R(hashCode: Long) は、1つのオブジェクトが hashCode() に2通りの答えを返していました。アクセサの値と、HashMap が使う Int の値です。getClass: Int も getClass() で同じことが起きていました。hashCode: Int、toString: String、getClass: Class と同じく、どちらもエラーになりました。

    // 以前: コンパイルでき、r.hashCode() は 5、(r as Object).hashCode() は 36
record R(hashCode: Long)

// 現在: E0010。成分の名前を変えてください。
record R(code: Long)
    • 表示されるもの: hashCode、toString、getClass の成分は、型にかかわらず成分の位置で E0010 になります。レコードでも enum の case でも同じです。
    • onion migrate の規則はありません: 新しい名前と、それを読むコードは利用者が決めるためです。

    抽象メソッドとインターフェースのメソッドのデフォルト値が型検査されるようになりました¶

    abstract def やインターフェースのメソッドのデフォルト値が使えるようになりました。呼び出しでその引数を省略できます。そのため、ほかのデフォルト値と同じく型検査されます。以前は使われることがなかったので、誤ったデフォルト値でもコンパイルできていました。

    // 以前: デフォルト値が使われないので、コンパイルできていました
abstract class A {
public:
  def this {}
  abstract def f(n: Int = "x"): Int
}

// 現在: "x" の位置で E0000。引数の型のデフォルト値を書いてください。
abstract class A {
public:
  def this {}
  abstract def f(n: Int = 0): Int
}
    • 表示されるもの: デフォルト値の位置で E0000（型が違う）または E0002（名前が見つからない）になります。
    • onion migrate の規則はありません: どのデフォルト値のつもりだったかは利用者にしかわからないためです。直すか、取り除いてください。

    toString / hashCode / equals を上書きするレコードのメソッドは、型を変えられなくなりました¶

    これまでレコードの本体では、Object のメソッドを別の戻り値の型で定義し直せました。クラスではできません。toString(): Int は生成された toString() を黙って消していました。toString(): String? は null を println まで届けていました。レコードもクラスと同じ規則に従うようになりました。

    // 以前: コンパイルでき、println(new R("")) は null を表示
record R(name: String) {
public:
  def toString(): String? = if name == "" { null } else { name }
}

// 現在: toString の位置で E0000。String を返してください。
record R(name: String) {
public:
  def toString(): String = if name == "" { "(none)" } else { name }
}
    • 表示されるもの:
    • 戻り値の型が別の参照型（String?、Object、CharSequence）のときは、メソッドの位置で E0000 になります。ヒントは、null になりうる値に ?: を使うよう勧めます。
    • どちらかの戻り値の型がプリミティブ型（toString(): Int、hashCode(): Long）のときは E0104 になります。
    • onion migrate の規則はありません: null の代わりに何を返すかは利用者が決めるためです。

    Http.Response は status() / body() / headers() だけで読むようになりました¶

    Http.Response には、同じ名前の公開フィールドとアクセサメソッドがありました。フィールドは非公開になりました。Server.Response や Proc.Result と同じです。

    val r = Http::getResponse("https://example.com")
println(r.status)     // これまでどおりコンパイルできる: status() を呼ぶ
println(r.status())   // 同じ呼び出し
    • Onion のソース: 変更は不要です。読めるフィールドがないので、r.status は status() を呼びます。
    • 表示されるもの: 古い onionc がフィールドを読むように生成した .class ファイルを実行すると、IllegalAccessError になります。再コンパイルしてください。
    • Java のコード: r.status()、r.body()、r.headers() と書いてください。
    • onion migrate の規則はありません: Onion の書き方はどれもそのままコンパイルできるため、書き換えるものがありません。

    1つの trait と型に対するインスタンスは、モジュールをまたいでも1つだけになりました¶

    ある trait のある型に対する instance は、プログラム全体で1回だけ宣言できます。 これまでは、別の module に2つ目を書いてもコンパイルでき、module 行のないファイルのものだけが使われていました。 今は2つ目がエラーになります。

    // shapes.on
module shapes;
trait Show[T] {
  def show(x: T): String
}
instance Show[Int] {
  def show(x: Int): String = "lib " + x
}

// app.on: 以前はコンパイルできた。今は E0097。このインスタンスか shapes.on のものを削除する。
module app;
import { shapes.Show }
instance Show[Int] {
  def show(x: Int): String = "app " + x
}
    • 表示されるもの: 2つ目のインスタンスで E0097 instance shapes.Show[java.lang.Integer] is already defined。
    • 直し方: インスタンスを1つだけ残し、もう1つを削除してください。
    • 同じパッケージの2つのファイル（どちらも module 行なし）では、これまでどおり E0008 duplicated class definition Show$$Integer になります。直し方は同じです。
    • 型の型引数: E0097 は外側の型だけを比べます。そのため Show[List[String]] と Show[List[Integer]] は同じインスタンスとみなされ、衝突します。
    • onion migrate の規則はありません: どちらのインスタンスを残すかは、あなたが決めることです。
