    Migrating to 1.0¶

    Onion is cleaning up its syntax and APIs before 1.0, while breaking a few programs is still cheap. Each breaking change is listed here with how to update your code.

    After 1.0, Onion keeps a compatibility promise: a program that compiles on 1.x keeps compiling and means the same thing on later 1.x releases.

    ret is now yield¶

    A do block's final value is written with yield.

    // Before
val sum = do[Option] { a <- getA(); b <- getB(); ret a + b }

// Now
val sum = do[Option] { a <- getA(); b <- getB(); yield a + b }
    • What changed: yield is a reserved word; ret is an ordinary identifier again.
    • What you see: old code reports local variable ret is not found., with a hint to write yield.
    • A Java method named yield: call it with backticks, e.g. Thread::`yield`().
    • Update a whole project: onion migrate src/ tests/ (or any files and directories). It rewrites only a do block's ret, never a variable named ret, a string or a comment.

    2147483648 needs a - directly in front¶

    The literal 2147483648 (and 9223372036854775808L) is valid only as the whole operand of a unary -, as in -2147483648. Anywhere else it used to wrap silently to the minimum value.

    // Before: compiled, with a surprising value
val a = 1 - 2147483648          // -2147483647, by wraparound
val b = -2147483648 as Long     // 2147483648: `as` binds tighter than `-`
val c = -2147483648 / 2         // 1073741824: `/` binds tighter than `-`

// Now
val a = 1 - 2147483648L         // or 1L - 2147483648L
val b = -2147483648L            // or (-2147483648) as Long
val c = (-2147483648) / 2       // -1073741824
    • What changed: the magnitude of the minimum value is checked where it is negated, not at the token.
    • What you see: integer literal out of range for Int (-2147483648..2147483647) -- add an L suffix to make it a Long literal., at the literal (... for Long ... with the L suffix).
    • Still fine: -2147483648, x + -2147483648, 3 * -2147483648, -9223372036854775808L, and hex or binary bit patterns such as 0x80000000.

    A decimal B/S literal must fit the signed range¶

    A decimal Byte literal now takes -128..127 and a decimal Short literal -32768..32767, as in Java. Larger values used to wrap silently.

    // Before: compiled, with a surprising value
val mask: Byte = 255B           // -1
val port: Short = 40000S        // -25536
val n = -128B as Int            // 128: `as` binds tighter than `-`

// Now
val mask: Byte = 0b11111111B    // -1, written as a bit pattern
val port: Int = 40000           // a Short cannot hold 40000
val n = (-128B) as Int          // -128
    • What changed: like 2147483648, the magnitudes 128B and 32768S are valid only as the whole operand of a -.
    • What you see: integer literal out of range for Byte (-128..127, or a bit pattern up to 0b11111111) -- ..., at the literal (... for Short ... with the S suffix).
    • Still fine: a binary bit pattern such as 0b11111111B, or a hex one with the S suffix such as 0xFFFFS.
    • Hex and B: in a hex literal B is a digit, never a suffix. 0xAB is the Int 171 and 0xFFB is the Int 4091. For a Byte, write 0b11111111B or -1B.
    • Where such a literal no longer fits a Byte (val x: Byte = 0xFFB, f(0xFFB) with a Byte parameter), the error carries a hint that says so.
    • Where it still fits, nothing is reported and the value changes: bs[0] = 0x1B stores 27 (was 1), and val y = 0x7FB is 2043 (was the Byte 127). Search your code for hex literals ending in B (0x...B).

    A quoted String in a config file is read without its quotes¶

    A shape name = config record now reads a String value written in double quotes as quoted text. This lets a value keep leading or trailing spaces through print and parse.

    # Before: the quotes were part of the value
name = "Alice"          # read as "Alice"  (7 characters)

# Now
name = "Alice"          # read as Alice    (5 characters)
name = "  Alice  "      # read as   Alice  (spaces kept)
name =   Alice          # read as Alice    (unquoted values are still trimmed)
name = "\"Alice\""      # read as "Alice"  (to keep literal quotes)
    • What changed: inside the quotes, \" is a quote and \\ is a backslash. Any other backslash is kept as it is, so "C:\temp" reads as C:\temp.
    • What you see: a file that already relied on literal quotes still parses, so there is no error or hint; the value just loses its outer quotes. Search your config files for values that start with ". A value with no closing ", or with a bare " inside it ("a" and "b"), is now a Defect naming the line.
    • Only String components: an Int, Boolean or other scalar is read exactly as before.

    A slot typed T accepts only a T¶

    Inside a generic class, assigning to a field, local or parameter typed by a type parameter T, initializing one, or returning from a method declared : T now accepts only a value of type T, as in Java. It used to accept anything that fit T's bound, and the program then threw a ClassCastException on the next read.

    class S[T, U] {
  var t: T
  var u: U
public:
  def this(x: T, y: U) { t = x; u = y }

  // Before: compiled, then `new S[String, Integer]("a", 1)` threw on the next read of t
  def f(): void { t = u }

  // Now: write the unchecked cast yourself, if the value really is a T
  def g(): void { t = (u as T) }
}
    • What changed: a value of an unrelated type variable (U), of the bound (Object, CharSequence), or of a concrete type ("x") no longer fits a T slot.
    • What you see: E0000 type T is expected, but type U is used. at the value.
    • Still fine: a T; a variable bounded by T ([T, U extends T], then t = u); null; and an argument to a Java method on a raw Java receiver ((o as ArrayList).add(u)). A value read back through one (t = (o as ArrayList).get(0)) is not a T, so it needs a cast.
    • Two parameters named T: a method's [T] inside class K[T] is a different T. The error then adds a hint saying so. To use the class's T, drop the method's [T].
    • Calls: an argument is checked when the method is inherited (set(o) inside Mid[U] extends Box[U]) or the receiver is typed with your variable (xs.add(o) with xs: List[T], b.set(o) with b: Box[T]).
    • A T? slot: it takes what a T slot takes, plus null and a T?. So o = u, o = uo (uo: U?) and o = "x" into o: T? are E0000 too (#2332). A constructor argument into a T? parameter (new Box[T](u) with def this(x: T?)) is E0021, as it already was for a T parameter.
    • Indexed assignments and literals: xs[0] = u and m["k"] = u into a List[T] or a Map[K, T] are E0000, as xs.set(0, u) already was (#2332). So is a literal [u], [t, u] or ["k": u] used as a List[T] or Map[K, T]; the error names the literal's type (List[U], or List[Object?] for a mix). Under a List[Object] target, [t, u] is still fine. Write [(u as T)] if the value really is a T.
    • Inherited members are now U: inside class Mid[U] extends Box[U], an inherited get(): T is a U (it was Object). U may be null, so get().toString() is now E0057, as it already was inside Box. Write get()?.toString(), get() ?: fallback, or give U a non-null bound: class Mid[U extends Object]. A Java superclass is the same: inside class MyList[T] extends ArrayList[T], get(0).toString() is now E0057.
    • this is a Mid[U]: inside class Mid[U], this keeps U, also through val me = this, id(this), [this] or () -> this. So same(this) fits an inherited same(o: Box[T]), and me.get() is a U (it was raw Mid, so me.get() was an Object).
    • Branches with different type arguments: if b { [t] } else { [u] } is a raw List. It compiles where an Object is expected; where a List[T] is expected, the [u] branch is E0000.
    • No onion migrate rule, on purpose: the only mechanical rewrite is inserting (u as T), which would hide exactly the bugs this check finds. Read each error and decide.

    An empty [] or [:] takes the type of its siblings¶

    In a list literal, or in the values of a map literal, an empty [] or [:] now has the type the other elements agree on. Before, it widened the whole literal to Object.

    val adj = [[1, 2], []]

// Before: List[Object], so adj[1].add(5) was E0005, and this compiled
adj.add("header")

// Now: List[List[Int]], so adj[1].add(5) compiles, and this is E0005
adj.add("header")

// To keep the old type, annotate it
val xs: List[Object] = [[1, 2], []]
    • What changed: the empty literal is typed after its siblings, from their type. Elements are still evaluated in source order.
    • What you see: E0005 naming List[List[Int]].add(String) (or Map[String, List[Int]].set(...)) where the code mixed element kinds, or passed the value to a List[Object] parameter.
    • Still fine: an explicit annotation wins, and a literal with no typed sibling ([[], []]) is typed as before.

    A lambda passed to overloaded extension methods no longer depends on declaration order¶

    When an extension declares the same method more than once, a lambda argument now picks the same overload whatever order the methods are declared in. Before, such a call often ran whichever overload was declared first or last. In general:

    • A call that compiled may now run a different overload, the one a class method would pick (with one difference, below). This mostly affects lambdas with untyped parameters.
    • A call that compiled may now be E0006, where two overloads fit equally.
    • To keep the old overload: give the lambda's parameters their types, pass the other argument with as (5 as Object, 2 as Double), pass the lambda as a typed value, or rename one method.

    Examples:

    Overloads Call Before Now To keep the old result
    z(f: (Object) -> void) on Object, z(o: Object) on String "abc".z((x: Object) -> …) String's z(Object) E0006 rename one method
    c(n: Long, g: (Long) -> Long), c(n: Object, g: (Long) -> Long) "a".c(5, (x: Long) -> x * 2L) obj or long:10, by order E0006 for long:10, "a".c(5L, …); for obj, "a".c(5 as Object, …)
    k(s: Supplier[String]), k(c: Callable[String]) "a".k { "v" } call or sup, by order E0006 for call, val c: Callable[String] = () -> "v", then "a".k(c); for sup, the same with val s: Supplier[String]
    f(o: Object, g) on String, f(s: String, g) on CharSequence "a".f("q", (x: Int) -> x) strobj1 E0006 "a".f("q" as Object, …)
    outer(f: (Int) -> Int), outer(f: Function[String, String]) (import { java.util.function.Function }) "a".outer { p -> ((q: Int) -> p).call(1) } os:s or oi:1, by order oi:1 val g: Function[String, String] = (p: String) -> …, then "a".outer(g)
    r(f: () -> void), r(o: Object) "a".r { IO::print("") } obj or fn, by order fn val h: () -> void = () -> …, then "a".r(h as Object)
    m(n: Int, f: (Int) -> Int), m(n: Object, f: (Object) -> Object) "a".m(1, { x -> x }) obj:1 or int:1, by order int:1 "a".m(1 as Object, { x -> x })
    k(n: Int, f: (Int) -> Int): Int, k(n: Double, f: (Double) -> Double): Double "a".k(2, { x -> x * 2 }) 4.0 (the Double one) 4 "a".k(2, (x: Double) -> x * 2.0)
    run(r: Runnable), run(c: Callable[Object]) "a".run { IO::print("") } callable:null runnable pass a typed Callable[Object] value
    • What changed: the overloads the lambda fits are ranked by one rule, written on issue #2447. It is the class-method rule, with one addition: a function-type parameter beats a SAM interface such as Function or Comparator (the outer row). A class method still reports E0006 there; #2472 tracks bringing classes onto the same rule.
    • What you see: E0006 method call is applicable for both …, with a hint naming the fixes in the last column.
    • Still fine: a call with one matching overload, or with no lambda argument.

    map and filter on any iterable return a List¶

    map and filter on a range, on map.values() or on any other Iterable that is not a List or a Set now return a List. Before, the result was typed Iterable, though it was already a list.

    val evens = (1..10).filter { x -> x % 2 == 0 }
evens.size                         // Before: E0004. Now: 5

var xs = (1..3).map { x -> x + 1 }
xs = new java.util.TreeSet[Int]()  // Before: compiled. Now: E0000

// To keep a variable that holds any iterable, declare its type
var ys: Iterable[Int] = (1..3).map { x -> x + 1 }
ys = new java.util.TreeSet[Int]()
    • What changed: Iterables::map(Iterable, f) and Iterables::filter(Iterable, p) return List[T]. A list's or a set's own map/filter is unchanged.
    • What you see: E0000 type List[Int] is expected, but type TreeSet[Int] is used, with a hint to declare var xs: Iterable[Int] = ....
    • Runs differently: with an overload or an extension on both Iterable and List, a call on the result now picks the List one. Rename one of them to keep the old choice.
    • Recompile: a class compiled against an older onion.jar that calls these methods throws NoSuchMethodError until it is compiled again.
    • Still fine: .toList() after such a pipeline still works, and the result still fits an Iterable parameter or variable.

    example and law are now contract predicates¶

    A check that runs when the build runs is a static def that returns Boolean and states ensures result. A predicate with parameters is sampled, as law was.

    // Before
record Pt(x: Int, y: Int) from re"(-?\d+),(-?\d+)" {
  law roundtrip(p: Pt) { Pt::parse(Pt::format(p)) == p }
  example { Pt::parse("3,4") == new Pt(3, 4) }
}

// Now
record Pt(x: Int, y: Int) from re"(-?\d+),(-?\d+)" {
public:
  static def roundtrip(p: Pt): Boolean
    ensures result
    = Pt::parse(Pt::format(p)) == p
  static def parsesThreeFour(): Boolean
    ensures result
    = Pt::parse("3,4") == new Pt(3, 4)
}
    • What changed: example and law are removed. At the top level, write def name(): Boolean ensures result = expr (no static). A body with several statements is a block that ends with return.
    • What you see: a false predicate is E0113. A parameter that cannot be sampled is also E0113, not a silent skip. --contracts is on by default (check).
    • Seed and samples: --law-seed and --law-samples are now --contract-seed and --contract-samples; --no-check-laws is gone (use --contracts off).
    • onion.Shape: a class that implements it no longer needs a predicate in its file (E0080 is retired).
    • Update a whole project: onion migrate src/ rewrites each law and example into this form.
    • A body of one expression becomes = expr; a longer body keeps its block, with return before the last statement.
    • An example with no name is named example1, example2, ... Rename it if you like.
    • A file that would not compile after the rewrite is left as written, and the command names the line.

    A field an invariant or history names is written only through this¶

    Contracts are a preview feature (RFC #2557). A field that a class's invariant or history names may be written only by that class's own code, through this. A write through any other object is E0110.

    class Clock {
public:
  var t: Int
  history t >= old(t)
  def this { t = 0 }
  def this(start: Int) { t = start }
  def advanceTo(k: Int): void { if k > t { t = k } }
}

// Before: compiled. Now: E0110 at `c`
//   val c = new Clock(); c.t = 5
// Now: pass the value to a constructor
val c = new Clock(5)

// Before: compiled. Now: E0110 at `o`
//   def sync(o: Clock): void { o.t = 9 }
// Now: call a method of that object; its own writes are checked
def sync(o: Clock): void { o.advanceTo(9) }
sync(c)
println(c.t)   // 9
    • What changed: each object keeps its own invariant and history, checked one call at a time. A write from outside that object's methods is one no such check can follow.
    • What you see: E0110, with the caret on the receiver (o, c, cs[0]). The message says to call a method of that object or set the value in a constructor.
    • Still fine: t = v, this.t = v, self.t = v, t++ and t += 1 in the class's own methods, also inside a lambda. Reading o.t from anywhere is fine too.
    • No onion migrate rule, on purpose: the fix adds a method or a constructor to the receiver's class, and which one fits is a design choice.

    A tool's requires sees more of what it runs¶

    onionc checks a tool's requires { ... } clause against the effects its body has. It now counts four things it missed before. A tool that relied on a miss gets E0077 (an effect missing from requires) or E0078 (a capability nothing uses).

    class Base {
public:
  def this {}
  def run(): Int = 1
}
class Loud extends Base {
public:
  def this {}
  override def run(): Int { IO::println("loud"); return 2 }
}

// Before: compiled. Now: E0077 at `b.run()`, "calling Loud::run"
//   tool go(): Int { val b: Base = new Base(); return b.run() }
// Now: declare what an override can do
tool go(): Int requires { console } {
  val b: Base = new Base()
  return b.run()
}
    What the tool does Before Now
    Calls a method a program class overrides (b.run() above) only the called method counted every program override counts too (E0077)
    Uses a class whose static initializer has an effect not counted counted (E0077)
    try (val r = new R()) { } where R is a program class close() not counted R::close counts (E0077)
    new Box[String]() of a program class unknown the constructor's own effects; an unknown kept only for it is E0078
    • What you see: E0077 names the call and the capability to add. E0078 names the capability to remove.
    • Not affected: what a library method might call back on an object you pass it (list.add(item) and Item::toString). Only the build's own check of contract predicates counts that.
    • No onion migrate rule, on purpose: the fix depends on what the called code does. Each error names the edit: add that capability, or remove the unused one.

    A record component named hashCode, toString or getClass must not change that method's type¶

    record R(hashCode: Long) gave one object two hashCode() answers: the accessor, and the Int one a HashMap uses. getClass: Int did the same to getClass(). Both are now errors, as hashCode: Int, toString: String and getClass: Class were.

    // Before: compiled, r.hashCode() = 5, (r as Object).hashCode() = 36
record R(hashCode: Long)

// Now: E0010. Rename the component.
record R(code: Long)
    • What you see: E0010 at the component, for hashCode, toString or getClass of any type, in a record or an enum case.
    • No onion migrate rule: the new name and the code that reads it are your choice.

    A default on an abstract or interface method is type-checked¶

    A default on an abstract def or an interface method now works: a call may omit that argument. So the default is now type-checked like any other default. Before, it was never used, and a wrong one compiled.

    // Before: compiled, because the default was never used
abstract class A {
public:
  def this {}
  abstract def f(n: Int = "x"): Int
}

// Now: E0000 at "x". Give a default of the parameter's type.
abstract class A {
public:
  def this {}
  abstract def f(n: Int = 0): Int
}
    • What you see: E0000 (wrong type) or E0002 (unknown name) at the default.
    • No onion migrate rule: only you know which default was meant. Fix it, or remove it.

    A record method that overrides toString, hashCode or equals must keep its type¶

    A record body could redefine an Object method with another return type. A class could not. toString(): Int silently dropped the generated toString(), and toString(): String? let a null reach println. A record now follows the class rule.

    // Before: compiled; println(new R("")) printed null
record R(name: String) {
public:
  def toString(): String? = if name == "" { null } else { name }
}

// Now: E0000 at toString. Return a String.
record R(name: String) {
public:
  def toString(): String = if name == "" { "(none)" } else { name }
}
    • What you see:
    • E0000 at the method when the return type is another reference type (String?, Object, CharSequence). Its hint suggests ?: for a nullable value.
    • E0104 when either return type is primitive (toString(): Int, hashCode(): Long).
    • No onion migrate rule: what to return instead of null is your choice.

    Http.Response reads through status(), body() and headers() only¶

    Http.Response had public fields and accessor methods with the same names. The fields are now private, as in Server.Response and Proc.Result.

    val r = Http::getResponse("https://example.com")
println(r.status)     // still compiles: calls status()
println(r.status())   // the same call
    • Onion source: nothing to change. With no field to read, r.status calls status().
    • What you see: an IllegalAccessError when you run a .class file built by an older onionc that read the field. Recompile it.
    • Java code: write r.status(), r.body() and r.headers().
    • No onion migrate rule: every Onion spelling still compiles, so there is nothing to rewrite.

    One instance per trait and type, across modules¶

    An instance of one trait for one type may be declared only once in the whole program. Before, a second one in another module compiled, and only the one in a file without a module line was ever used. Now the second one is an error.

    // shapes.on
module shapes;
trait Show[T] {
  def show(x: T): String
}
instance Show[Int] {
  def show(x: Int): String = "lib " + x
}

// app.on: Before, compiled. Now E0097. Delete this instance, or the one in shapes.on.
module app;
import { shapes.Show }
instance Show[Int] {
  def show(x: Int): String = "app " + x
}
    • What you see: E0097 instance shapes.Show[java.lang.Integer] is already defined, at the second instance.
    • Fix: keep one instance and delete the other.
    • Two files in the same package (both without a module line) still give E0008 duplicated class definition Show$$Integer. The fix is the same.
    • Type arguments of the type: E0097 compares only the outer type, so Show[List[String]] and Show[List[Integer]] are one instance and clash.
    • No onion migrate rule: which instance to keep is your choice.
